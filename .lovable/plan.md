
# دعم الفروع المتعددة (Multi-Branch)

الهدف: كل شركة (agency) يكون لها عدة فروع في ولايات مختلفة، كل فرع يعمل باستقلال في العمليات اليومية، مع مشاركة الأسطول والموارد على مستوى الشركة، وتحكّم واضح بالصلاحيات.

## 1. النموذج البياني

جدول جديد `branches`:
- `id`, `agency_id`, `name` (مثل «فرع الخرطوم»)، `state` (الولاية)، `address`، `phone`، `is_main` (الفرع الرئيسي)، `created_at`, `updated_at`.

إضافة عمود `branch_id` على الجداول ذات **العمليات الخاصة بالفرع**:
- `bookings`, `cashier_shifts`, `expenses` → `branch_id NOT NULL` (بعد ترحيل البيانات القديمة إلى فرع افتراضي).
- `profiles` → `branch_id` (الفرع الذي ينتمي إليه المستخدم؛ للمالك يبقى NULL = وصول لكل الفروع).
- `user_roles` → `branch_id` اختياري (للأدوار المقيّدة بفرع).
- `notifications` → `branch_id` اختياري (إشعارات على مستوى فرع أو الشركة كلها).

الموارد **المشتركة** تبقى كما هي بدون `branch_id`:
- `buses`, `drivers`, `routes`, `trips` (لأن الباص قد يتحرك بين الولايات).

ترحيل البيانات: إنشاء فرع رئيسي واحد لكل شركة موجودة وربط جميع السجلات القديمة به تلقائياً.

## 2. الأدوار والصلاحيات

إضافة قيمة `branch_manager` إلى `app_role`. الأدوار النهائية:
- `owner`: يرى كل الفروع، يبدّل بينها، يضيف/يحذف فروع ومستخدمين، يعدّل الأسطول.
- `branch_manager`: مقيّد بفرعه — يرى تقارير/وردياته/حجوزاته/مصروفاته فقط، يضيف كاشير داخل فرعه.
- `cashier`: مقيّد بفرعه — POS ووردياته فقط.

دوال أمان جديدة (SECURITY DEFINER):
- `current_branch_id()` — يقرأ `branch_id` من `profiles` للمستخدم الحالي.
- `user_can_access_branch(_branch uuid)` — true إذا كان المالك أو `branch_id` مطابق.
- تحديث `has_role` ليقبل `_branch_id` اختيارياً.

**سياسات RLS جديدة** على جميع الجداول ذات `branch_id`:
- المالك: وصول لكل فروع شركته (الحالي).
- غير المالك: `agency_id = current_agency_id() AND branch_id = current_branch_id()`.
- منح (GRANT) صريح مع كل جدول جديد/معدَّل.

## 3. اختيار الفرع النشط (UI)

- في `AppShell` أعلى الصفحة: شارة/زر «فرع: كذا» بجانب اسم الشركة.
- **المالك**: قائمة منسدلة لتبديل الفرع النشط (يُحفظ في `localStorage` + hook `useActiveBranch`). كل الاستعلامات تفلتر بـ `activeBranchId`.
- **مدير الفرع/الكاشير**: الشارة تعرض اسم فرعه فقط بدون تبديل.
- عند إنشاء أي حجز/وردية/مصروف: يُملأ `branch_id` تلقائياً من الفرع النشط.

## 4. صفحات وميزات جديدة

- **إدارة الفروع** (`/branches` — للمالك فقط): قائمة الفروع، إضافة/تعديل/حذف، تعيين الفرع الرئيسي.
- **الموظفون**: إضافة عمود «الفرع» عند إنشاء مستخدم، وفلترة القائمة حسب الفرع النشط.
- **التقارير ولوحة التحكم**: كل الأرقام تُفلتر تلقائياً بالفرع النشط؛ للمالك خيار «كل الفروع» يُظهر إجمالي الشركة + تفصيل لكل فرع.
- **الحجوزات/الوردايات/المصروفات/POS**: كلها تعمل ضمن الفرع النشط تلقائياً.
- **التذكرة المطبوعة**: إضافة اسم الفرع في الترويسة.

## 5. تفاصيل تقنية

```text
agencies ──┬─ branches (جديد)
           │     ├─ profiles.branch_id
           │     ├─ user_roles.branch_id
           │     ├─ bookings.branch_id
           │     ├─ cashier_shifts.branch_id
           │     └─ expenses.branch_id
           │
           └─ buses / drivers / routes / trips  (مشتركة)
```

- Hook جديد: `useActiveBranch()` يُرجع `{ branchId, branchName, canSwitch, setBranch, branches }`.
- كل `useQuery` مفتاحه سيتضمن `activeBranchId` لتفادي التخزين المؤقت بين الفروع.
- سياسة تفرد المقعد للحجز: تبقى على `(trip_id, seat_number)` (لأن الرحلات مشتركة، فرعان لا يبيعان نفس المقعد).
- تحديث `handle_new_user` و`create_agency_for_current_user` لإنشاء فرع رئيسي تلقائياً وربط المالك به.

## 6. خطوات التنفيذ (بالترتيب)

1. Migration: جدول `branches` + إضافة `branch_id` للجداول + ترحيل بيانات + إضافة role `branch_manager` + دوال + RLS.
2. تحديث `useAgencyId` وإضافة `useActiveBranch` + مبدّل الفرع في `AppShell`.
3. صفحة `/branches` (CRUD + تعيين رئيسي).
4. تحديث صفحة الموظفين لإسناد فرع.
5. تمرير `branch_id` في كل عمليات الإدراج (POS، الوردايات، المصروفات).
6. تحديث الفلاتر في لوحة التحكم/التقارير/الحجوزات/الوردايات/المصروفات حسب الفرع النشط.
7. إضافة اسم الفرع في التذكرة المطبوعة.
